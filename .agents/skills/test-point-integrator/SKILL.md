## 目标

将 M 分析、F 分析、Q 分析产出的测试点按模块归集，
执行完整覆盖检查，将具有相同测试逻辑的测试点合并为逻辑用例，
并为每个逻辑用例分配测试数据。

## 适用范围

- 适用阶段：MFQ 分析的 integration 阶段
- 输入：`.workflow-meta/mfq/m-analysis/` + `.workflow-meta/mfq/f-analysis/` + `.workflow-meta/mfq/q-analysis/`
- 输出：`.workflow-meta/mfq/integration/` 目录下多个文件

## 前置条件

- [ ] M 分析完成（`m-analysis/test-points.md` 存在）
- [ ] F 分析完成（`f-analysis/coupling-test-points.md` 存在）
- [ ] Q 分析完成（`q-analysis/quality-test-points.md` 存在）

## 执行流程

### 步骤 1：测试点归集

按四级/五级目录归集所有来源的测试点：

```
模块 A
├── 子模块 A1
│   ├── TP-M-A1-001 (M分析)
│   ├── TP-M-A1-002 (M分析)
│   ├── TP-F-A1-B2-001 (F分析 - 与B2的耦合)
│   └── TP-Q-REL-001 (Q分析 - 可靠性)
└── 子模块 A2
    ├── TP-M-A2-001 (M分析)
    └── TP-Q-SEC-001 (Q分析 - 安全性)
```

### 步骤 2：覆盖检查

**需求层覆盖**（逐条核验）：

| 检查项 | 方法 |
|--------|------|
| 每条 SR 至少 1 个测试点 | 遍历 SR 列表，检查 TP 的关联需求字段 |
| SR 描述的每个功能行为 | 逐条比对 SR 描述与 TP 描述的语义覆盖 |

**场景层覆盖**：
- 每个已确认场景的关键路径至少 1 个测试点

**覆盖判定规则**（CF-05）：
- `新增用例`：必须设计用例的测试点
- `合并`：合并到某条逻辑用例中（注明合并目标）
- `不设计用例`：例外情况，应极少出现，需标注理由

### 步骤 3：测试逻辑识别与合并

识别具有相同测试逻辑的测试点：

**合并条件**（满足以下任一）：
1. 测试步骤相同，仅测试数据不同
2. 验证的功能行为相同，仅输入参数/配置不同
3. 属于同一功能在不同条件下的验证

**合并规则**：
- 被合并的测试点标记为 `合并` 状态，注明合并到哪个逻辑用例
- 合并后的逻辑用例继承所有被合并测试点的需求关联
- 不同模块的测试点不合并（即使逻辑相同）

### 步骤 4：逻辑用例生成

为每组合并后的测试逻辑生成逻辑用例：

| 字段 | 说明 |
|------|------|
| LC-ID | 逻辑用例编号 `LC-<模块>-<子模块>-NNN` |
| 测试逻辑 | 描述测试的核心逻辑/步骤 |
| 包含测试点 | 合并的 TP-ID 列表 |
| 关联需求 | 所有关联的 SR 编号 |
| 所属模块 | 四级目录 |
| 所属子模块 | 五级目录 |

### 步骤 5：测试数据分配

为每个逻辑用例分配测试数据集：

| 字段 | 说明 |
|------|------|
| TD-ID | 测试数据编号 `TD-<LC-ID>-NNN` |
| 逻辑用例 | 关联的 LC-ID |
| 数据描述 | 测试数据的业务含义 |
| 具体数据 | 参数名=值 的列表 |
| 覆盖的测试点 | 本条数据覆盖的 TP-ID |

### 步骤 6：输出

写入 `.workflow-meta/mfq/integration/` 目录：

| 文件 | 内容 |
|------|------|
| `all-test-points.md` | M+F+Q 按模块归集的全量测试点 |
| `logic-cases.md` | 逻辑用例列表（LC-ID / 逻辑 / 测试点 / 需求） |
| `test-data.md` | 测试数据列表（TD-ID / LC-ID / 数据 / 覆盖TP） |
| `coverage-matrix.md` | SR→TP→LC→TD 的追踪矩阵 |

## 输出格式参考

### all-test-points.md

```markdown
# <特性名> — 测试点整合表

## 统计

| 来源 | 测试点数 |
|------|---------|
| M 分析 | N |
| F 分析 | M |
| Q 分析 | K |
| 合计 | N+M+K |

## 测试点整合

| TP-ID | 描述 | 来源 | 模块 | 子模块 | 关联SR | 覆盖判定 | 归属LC |
|-------|------|------|------|--------|--------|---------|--------|
| TP-M-001 | ... | M | ... | ... | SR-001 | 新增 | LC-001 |
| TP-M-002 | ... | M | ... | ... | SR-001 | 合并→LC-001 | LC-001 |
```

## Gotchas

- 覆盖检查必须是逐条语义对比，不能只看编号关联
- 合并时注意保留所有来源的追踪关系
- F 分析的耦合测试点可能跨模块，需要决定归属到哪个模块
- Q 分析的测试点可能适用于多个模块，需在每个相关模块都有体现

## 验收标准

- [ ] M+F+Q 测试点全部归集且无遗漏
- [ ] 需求覆盖率 = 100%（所有 SR 至少 1 个 TP）
- [ ] 逻辑用例合并后无重复测试逻辑
- [ ] 每个逻辑用例至少 1 组测试数据
- [ ] 追踪矩阵 SR→TP→LC→TD 链路完整
- [ ] 输出文件写入 `.workflow-meta/mfq/integration/`
