# SCOPE-Pack 跨平台用户级统一指令 / Skill / 工具方案（Codex / Claude Code）

> 目标：将当前项目整理为 **Codex** 与 **Claude Code** 可共用的**用户级**能力包，并可在 **Windows / Linux** 上稳定使用。
>
> 范围说明：**本轮只关注 Codex 与 Claude Code**；**Copilot CLI 暂时不考虑**。
>
> 参考输入：`.input/doc-unification-remediation-plan.md`、`docs/20260419_Codex-Claude-Code-配置文件梳理与对照.md`

---

## 1. 问题定义

当前仓库已经具备一定的跨平台安装基础：

- 交付源目录已经收敛到 `agents/`、`skills/`、`rules/`
- `scripts/install.py` 已支持多种 agent 平台与 `--scope user`
- 已有将共享内容安装到用户目录的基本能力

但如果目标变为：

> **一套用户级安装，多个项目复用，同时兼容 Codex 与 Claude Code，且可在 Windows / Linux 上稳定运行**

那么当前方案仍然不够，主要阻塞点不再只是“文件复制”，而是**两种平台的真实配置发现面完全不同**。

### 1.1 当前阻塞点

| 阻塞点 | 当前现状 | 影响 |
|---|---|---|
| 相对路径依赖 | 多个 Agent / Skill 仍直接引用 `agents/templates/...`、`scripts/...`、`.output/...` | 用户级安装后，在任意项目目录运行时容易断链 |
| 工具未作为共享运行时交付 | 现有安装更偏“复制说明文件”，共享脚本与模板没有形成稳定 runtime | “指令能看见，工具不能跑” |
| 旧方案把两平台看得过于相似 | 旧文档按“平台目录薄包装”统一处理，但没充分区分 Codex 与 Claude Code 的真实配置入口 | 渲染目标会选错，甚至写到不该写的文件 |
| 用户状态与配置没有分离 | 例如 Claude 的 `~/.claude.json`、Codex 的 `auth.json` / history / memories 属于运行时状态 | 如果当成“安装目标”直接覆盖，会破坏用户环境 |
| Python 入口未统一 | 仓库文档要求 `uv`，但脚本侧仍存在系统 `python` 作为默认路径的倾向 | Windows / Linux 行为不完全一致 |

### 1.2 为什么旧的“统一复制”思路不够

旧思路默认：

1. 各平台都有一个“用户目录”
2. 只要把文件复制进去就能被发现
3. 平台之间主要差异只是文件格式

但基于本轮文档分析，这个假设并不成立：

- **Codex** 的核心入口是 `~/.codex/config.toml` + `~/.codex/AGENTS.md` + `~/.codex/hooks.json` + `~/.codex/rules/*.rules` + `~/.agents/skills/**`
- **Claude Code** 的核心入口是 `~/.claude/settings.json` + `~/.claude/CLAUDE.md` + `~/.claude/skills/**` + `~/.claude/agents/**`
- **Claude 的 `~/.claude.json` 不是主设置文件，而是全局状态文件**，里面包含 OAuth、MCP、主题、per-project state，不应作为常规渲染目标
- **Codex 的 `.rules` 是命令执行策略文件**，而 **Claude 的 `.claude/rules/*.md` 是规则文档 / 记忆片段**，两者不能视作同一种产物

因此，本轮方案必须从“通用复制模型”改为：

> **共享 runtime + 双平台定向适配 + 用户状态文件保护**

## 2. 目标边界

### 2.1 本轮目标

1. **单一来源维护**：共享规则、共享 Skill、共享工具只维护一套源
2. **用户级复用**：安装一次后，可在多个项目中复用
3. **双平台薄适配**：只为 **Codex** 与 **Claude Code** 生成平台发现入口
4. **跨系统可用**：Linux 与 Windows 使用同一套逻辑、不同路径映射
5. **运行时可落地**：不仅能安装说明文件，还能真正调用共享工具
6. **保护用户状态**：不覆盖认证、历史、缓存、OAuth、per-project state 等用户运行时数据

### 2.2 非目标

1. **本轮不考虑 Copilot CLI**
2. 不在本轮引入新的包管理体系替换 `uv`
3. 不把任何项目输出目录改造成用户级共享目录
4. 不改变现有 meta 工作流状态机和 Story 生命周期
5. 不尝试把 Codex 与 Claude Code 的所有平台文件强行收敛成同一种产物格式
6. 不把 `~/.claude.json`、`~/.codex/auth.json`、`history.jsonl`、`memories/` 视为安装产物
7. 不优先建设 Claude 的 legacy `.claude/commands/*.md` 体系；**本轮优先 skills**

## 3. 平台事实基线

本节是方案设计的前提。它不是实现细节，而是当前文档分析得出的**必须遵守的发现面**。

### 3.1 Codex 的关键发现面

| 类别 | 用户级位置 | 说明 |
|---|---|---|
| 主配置 | `~/.codex/config.toml` | Codex 主配置入口，管理模型、provider、sandbox、approval、MCP、agents、skills config 等 |
| 持久指令 | `~/.codex/AGENTS.md` / `~/.codex/AGENTS.override.md` | 用户级全局指令层 |
| 项目指令 | 项目路径链上的 `AGENTS.md` / `AGENTS.override.md` | 从 project root 到 cwd 逐层发现 |
| Hooks | `~/.codex/hooks.json` | 需在 `config.toml` 中开启 `features.codex_hooks = true` |
| Rules | `~/.codex/rules/*.rules` | 可执行命令规则，Starlark 格式 |
| Skills | `~/.agents/skills/<skill-name>/SKILL.md` | 用户级技能不在 `~/.codex/skills/`，而在 `~/.agents/skills/` |
| 认证 / 状态 | `~/.codex/auth.json`、`history.jsonl`、`memories/` | 运行时状态，不应被覆盖 |

### 3.2 Claude Code 的关键发现面

| 类别 | 用户级位置 | 说明 |
|---|---|---|
| 主配置 | `~/.claude/settings.json` | Claude Code 主设置入口 |
| 持久指令 | `~/.claude/CLAUDE.md` | 全局持久指令 / 记忆层 |
| Skills | `~/.claude/skills/<skill-name>/SKILL.md` | 用户级技能 |
| Agents | `~/.claude/agents/*.md` | 用户级 subagents |
| Output styles | `~/.claude/output-styles/*.md` | 用户级输出风格，可选 |
| 全局状态 | `~/.claude.json` | OAuth、MCP、主题、editor mode、per-project state、缓存等；**不是常规安装目标** |
| MCP（用户 / 本地作用域） | `~/.claude.json` | 与 settings 分离，需谨慎处理 |
| MCP（项目作用域） | `.mcp.json` | 项目共享，不属于用户级安装产物 |

### 3.3 两平台的关键差异

| 维度 | Codex | Claude Code | 设计含义 |
|---|---|---|---|
| 主配置格式 | TOML | JSON | 不能共用同一渲染模板 |
| 主指令文件 | `AGENTS.md` | `CLAUDE.md` | 需要分别渲染 |
| Rules | `.rules`（可执行策略） | `.claude/rules/*.md`（规则文档） + `settings.json.permissions`（硬权限） | 不能把同一份 rules 直接复制过去 |
| Hooks | 独立 `hooks.json` | `settings.json` 中的 `hooks` 字段 | 适配方式不同 |
| Skills 用户级目录 | `~/.agents/skills/` | `~/.claude/skills/` | 安装器目标目录不同 |
| 用户状态文件 | `auth.json` / history / memories | `~/.claude.json` | 必须排除出“托管渲染”范围 |

## 4. 候选方案

### 4.1 方案 A：继续分别复制到各平台用户目录

做法：

- 把 `agents/`、`skills/`、`rules/`、`scripts/` 分别复制到 Codex 和 Claude 的用户目录
- 平台目录既是发现入口，也是“事实上的维护副本”

优点：

- 实现最简单
- 不需要引入共享运行时根目录

缺点：

- Codex 与 Claude 的目录结构并不对称，硬复制会越来越多平台分支
- 工具、模板、规则会重复拷贝，长期容易漂移
- 很难保护用户已有配置与状态文件
- 对 Codex 的 `config.toml` / Claude 的 `settings.json` 都会产生覆盖风险

### 4.2 方案 B：共享运行时根目录 + 双平台薄适配层（推荐）

做法：

1. 新增一个**用户级共享运行时根目录**
2. `agents/`、`skills/`、`rules/`、`scripts/`、`templates/` 统一安装到该根目录
3. 仅为 **Codex** 与 **Claude Code** 生成各自的用户级发现入口
4. 平台入口文件由共享 runtime 渲染而来，但**不覆盖用户状态文件**
5. 对已有 `config.toml` / `settings.json` 采用**最小写入 / 可控 merge**策略，而不是整文件替换

优点：

- 真正做到“一套源，两端共用”
- 工具和模板只装一次
- 升级、回滚、校验都能围绕一个共享根进行
- 平台差异被收敛到适配层，而不是扩散到业务源目录

缺点：

- 需要引入渲染步骤和路径占位符
- 需要实现对 TOML / JSON 的安全 merge
- 需要明确区分“配置文件”和“状态文件”

### 4.3 推荐结论

**推荐采用方案 B。**

原因：用户要的是“共用的用户级指令、Skill、工具”，核心不是“复制文件到两个目录”，而是：

> **建立一个共享 runtime，再把 Codex 与 Claude Code 各自接到这个 runtime 上，同时避免破坏用户原有状态文件。**

## 5. 推荐架构

### 5.1 三层结构

```text
Layer 1: Canonical Source
  agents/
  skills/
  rules/
  scripts/
  templates/

Layer 2: Shared Runtime Home
  ~/.scope-pack/                (Linux)
  %USERPROFILE%\.scope-pack\    (Windows)

Layer 3: Platform Adapters
  Codex surfaces
  Claude Code surfaces
```

含义：

- **Layer 1**：仓库内唯一维护源
- **Layer 2**：用户级共享运行时，Codex 与 Claude Code 共用
- **Layer 3**：平台专属发现入口，仅承载格式、目录和发现机制差异

### 5.2 用户级共享运行时目录

本方案建议区分两种模式：

1. **开发联动模式（推荐给当前仓库）**
2. **发布安装模式（用于稳定发布到用户目录）**

对于你当前这个仓库，推荐使用**开发联动模式**：

> **当前项目目录本身就是 `SCOPE_PACK_HOME`。**

这样做的好处是：

- 你直接在当前仓库里修改 agent / skill / tool / template
- 用户级入口只做“发现与转发”
- 修改后无需手工复制多份，其他 agent 平台会同步使用最新版本

#### 开发联动模式目录

```text
<THIS_REPO_ROOT>/
  agents/
  skills/
  rules/
  scripts/
  templates/
  .scope-pack-dev/
    codex/
      AGENTS.md
      hooks.json
      rules/
        scope-pack.rules
      config.fragment.toml
    claude-code/
      CLAUDE.md
      settings.fragment.json
    links-manifest.json
```

说明：

- `agents/`、`skills/`、`rules/`、`scripts/`、`templates/`：**可编辑 canonical source**
- `.scope-pack-dev/`：**自动生成的适配层与同步产物**，不直接手改
- `links-manifest.json`：记录用户目录里创建了哪些链接 / 薄包装 / managed fragment

#### 发布安装模式目录

当后续需要做稳定安装包时，再使用独立的用户级共享目录：

```text
<SCOPE_PACK_HOME>/
  manifest.json
  runtime/
    agents/
    skills/
    rules/
    scripts/
    templates/
      shared/
        fragments/
        files/
      codex/
      claude-code/
  state/
    logs/
    cache/
  bin/
    scope-pack
    scope-pack.ps1
```

说明：

- `runtime/agents/`：共享 Agent / prompt 源
- `runtime/skills/`：共享 Skill 源
- `runtime/rules/`：共享规则正文与渲染来源
- `runtime/scripts/`：共享工具脚本
- `runtime/templates/`：共享模板根目录，**仅供 runtime 内部使用，不直接暴露给目标项目**
- `state/`：运行日志、缓存、临时状态；仍放在用户目录，不污染目标项目
- `manifest.json`：记录版本、渲染时间、安装平台、路径映射
- `bin/`：统一入口包装器，屏蔽 Windows / Linux 命令差异

**建议结论：**

- **当前开发阶段：用开发联动模式**
- **发布给其他用户或机器：再切到发布安装模式**

### 5.3 共享 templates 目录设计

`templates/` 不再建议挂在 `agents/templates/` 下，而应升级为**独立顶层模板域**。原因是它服务的不只是 agent，还包括：

- 规则正文渲染
- 平台配置文件渲染
- skill / tool 生成文件
- 目标项目根目录输出文件骨架

建议结构如下：

```text
templates/
  shared/
    fragments/
      instructions/
      workflow/
      paths/
      safety/
    files/
      root/
      docs/
      config/
  codex/
    AGENTS.md.tmpl
    config.toml.tmpl
    hooks.json.tmpl
    rules/
      default.rules.tmpl
  claude-code/
    CLAUDE.md.tmpl
    settings.json.tmpl
    skill/
      SKILL.md.tmpl
    agent/
      agent.md.tmpl
```

#### `templates/shared/fragments/`

用于存放**内部拼装片段**，特点是：

- 只给渲染器、installer、tool 使用
- **不会直接写入目标项目**
- 不应出现源仓库专有路径、仓库名、调试信息

典型内容：

- 通用指令段
- 工作流片段
- 路径约定片段
- 安全说明片段

#### `templates/shared/files/`

用于存放**可被工具渲染成最终文件**的骨架模板，特点是：

- 目标是生成到**运行项目根目录**
- 文件内容必须对目标项目“自解释”
- 不泄露本仓库内部目录结构

建议再分：

- `root/`：生成到项目根目录的文件模板
- `docs/`：生成到目标项目 `docs/` 的模板
- `config/`：生成到目标项目标准配置路径的模板

#### `templates/codex/` 与 `templates/claude-code/`

用于存放**平台适配模板**，特点是：

- 只描述平台发现入口与平台格式差异
- 不混入共享业务正文，正文由 `shared/fragments/` 注入
- 渲染结果进入用户级入口或目标项目根目录下的标准平台路径
### 5.4 平台适配层目标

#### Codex 适配层

| 目标位置 | 作用 | 是否建议托管 |
|---|---|---|
| `~/.codex/AGENTS.md` | 用户级全局指令 | 是 |
| `~/.codex/config.toml` | 主配置入口 | 是，但必须最小 merge，不可粗暴覆盖 |
| `~/.codex/hooks.json` | Hooks | 是 |
| `~/.codex/rules/*.rules` | 执行策略 | 是 |
| `~/.agents/skills/**` | 用户级 Skills | 是 |
| `~/.codex/auth.json` | 认证缓存 | 否 |
| `~/.codex/history.jsonl` / `memories/` | 历史 / 记忆 | 否 |

#### Claude Code 适配层

| 目标位置 | 作用 | 是否建议托管 |
|---|---|---|
| `~/.claude/CLAUDE.md` | 用户级持久指令 | 是 |
| `~/.claude/settings.json` | 主设置入口 | 是，但必须最小 merge，不可粗暴覆盖 |
| `~/.claude/skills/**` | 用户级 Skills | 是 |
| `~/.claude/agents/**` | 用户级 Agents | 是 |
| `~/.claude/output-styles/**` | 输出风格（可选） | 可选 |
| `~/.claude.json` | OAuth / MCP / 全局状态 | 否 |

**关键原则：**

> 适配层只托管“平台发现入口”和“明确可管理的配置面”，不托管用户认证、历史、缓存、per-project state。

## 6. 路径模型与运行时约定

这是本方案能否真正落地的关键。

### 6.1 运行项目根目录是唯一可见输出根

当 SCOPE-Pack 作为**独立项目**安装到用户环境、再去服务其他开发项目时，应遵守：

> **SCOPE-Pack 的内部信息对目标开发项目默认不可见。**

这意味着：

1. 共享脚本、共享模板、共享规则正文、渲染缓存，全部留在 `SCOPE_PACK_HOME`
2. 目标项目中只出现**真正需要被该项目使用或提交的文件**
3. 不再默认创建 `.input/`、`.output/`、`templates/`、`scripts/` 这类暴露 SCOPE-Pack 内部结构的目录

目标项目中的**可见输出面**应收敛为：

- 项目根目录文件，例如 `AGENTS.md`、`CLAUDE.md`
- 项目根目录下的平台标准隐藏目录，例如 `.claude/`、`.codex/`
- 业务工具明确要求生成到根目录或 `docs/` 等标准位置的文件

不建议出现在目标项目中的内容：

- `SCOPE_PACK_HOME` 路径
- 本仓库目录名、源仓库绝对路径
- 调试日志、render cache、模板片段目录
- `.output/` 这类仅对 SCOPE-Pack 自身有意义的运行目录

原因：

- 目标项目只需要消费结果，不需要知道 SCOPE-Pack 的内部组织结构
- 这样可以降低噪音、减少误提交、降低“外来元工作流痕迹”
- 也更符合“用户级安装，跨项目复用”的隔离原则

### 6.2 引入共享运行时路径变量

安装器渲染时统一注入以下变量：

- `{{SCOPE_PACK_HOME}}`：共享运行时根目录；在**开发联动模式**下等于当前仓库根目录，在**发布安装模式**下等于用户级安装目录
- `{{SCOPE_PACK_RUNTIME}}`：`{{SCOPE_PACK_HOME}}/runtime`；开发联动模式下可直接视为 `{{SCOPE_PACK_HOME}}`
- `{{SCOPE_PACK_SCRIPTS}}`：`{{SCOPE_PACK_RUNTIME}}/scripts`
- `{{SCOPE_PACK_TEMPLATES}}`：`{{SCOPE_PACK_RUNTIME}}/templates`
- `{{SCOPE_PACK_TEMPLATES_SHARED}}`：`{{SCOPE_PACK_TEMPLATES}}/shared`
- `{{SCOPE_PACK_DEV_SYNC}}`：开发联动模式下的适配层目录，默认是 `{{SCOPE_PACK_HOME}}/.scope-pack-dev`
- `{{PROJECT_ROOT}}`：当前运行目标项目根目录
- `{{PROJECT_OUTPUT_ROOT}}`：默认等于 `{{PROJECT_ROOT}}`

约束：

1. **引用模板和工具时必须使用 `SCOPE_PACK_HOME` 体系**
2. **所有最终输出文件默认写到 `PROJECT_OUTPUT_ROOT`，也就是运行项目根目录**
3. 只有平台标准目录可以作为根目录下的例外，例如 `.claude/`、`.codex/`
4. **禁止把 `SCOPE_PACK_HOME`、源仓库路径、内部模板目录暴露到最终输出**
5. **禁止把用户状态文件路径写死进业务规则**

#### 6.2.1 这些路径变量主要存放什么

| 变量 | 主要内容 | 说明 |
|---|---|---|
| `SCOPE_PACK_HOME` | 当前仓库或发布安装根 | 统一定位共享能力源 |
| `SCOPE_PACK_RUNTIME` | 运行资源目录 | agents、skills、rules、scripts、templates |
| `SCOPE_PACK_SCRIPTS` | 工具脚本 | Python / Shell 工具 |
| `SCOPE_PACK_TEMPLATES` | 模板目录 | 平台模板与共享模板 |
| `SCOPE_PACK_DEV_SYNC` | 开发联动同步产物 | 用户目录链接清单、配置片段、渲染后的薄包装 |
| `PROJECT_OUTPUT_ROOT` | 目标项目输出根 | 默认就是运行项目根目录 |

#### 6.2.2 易用的修改与同步方案（推荐）

推荐采用：

> **“源码直改 + 用户目录软链接 / 薄包装 + 一键 sync”**

具体做法：

1. **你只修改当前仓库中的 canonical source**
   - `agents/`
   - `skills/`
   - `rules/`
   - `scripts/`
   - `templates/`
2. **不要手改用户目录**
   - `~/.codex/`
   - `~/.agents/skills/`
   - `~/.claude/`
3. 用一个统一命令刷新适配层，例如：
   - `uv run python scripts/install.py --mode dev-link --refresh`
   - 或包装成 `bin/scope-pack sync`

这个 `sync` 命令负责：

1. 重新渲染 `.scope-pack-dev/codex/*` 与 `.scope-pack-dev/claude-code/*`
2. 刷新用户目录中的软链接
3. 对 `~/.codex/config.toml`、`~/.claude/settings.json` 做**最小 merge**
4. 不碰 `~/.claude.json`、Codex `auth.json`、history、memories

#### 6.2.3 哪些修改会“立即同步”，哪些需要 `sync`

| 修改类型 | 是否立即生效 | 说明 |
|---|---|---|
| 修改 `agents/`、`skills/`、`scripts/` 中被用户目录直接软链接的源文件 | 基本是 | 重启对应 agent session 后即可使用最新内容 |
| 修改 `rules/AGENTS.md`、`rules/CLAUDE.md` 这类直接链接的入口文件 | 基本是 | 重启会话后生效 |
| 修改 `templates/` | 否 | 因为模板要重新渲染产物，需要执行 `sync` |
| 修改平台配置片段（如 hooks / settings fragment / config fragment） | 否 | 需要执行 `sync`，把新片段 merge 到用户入口 |

#### 6.2.4 为什么这个方案易用

因为它把“编辑”和“分发”分开了：

- **编辑面**永远只有当前仓库一份
- **分发面**永远通过 `.scope-pack-dev/` 和用户目录链接自动同步
- 你不需要记忆“改完还要复制到哪里”

#### 6.2.5 冲突控制

为避免和用户自己的平台配置冲突，建议遵守：

1. **源文件尽量软链接**
   - `~/.claude/skills/<name>` → 当前仓库 `skills/<name>`
   - `~/.claude/agents/<name>.md` → 当前仓库 `agents/<name>.md`
   - `~/.agents/skills/<name>` → 当前仓库 `skills/<name>`
2. **配置文件只做 managed fragment merge**
   - `~/.codex/config.toml`
   - `~/.claude/settings.json`
3. **状态文件不托管**
   - `~/.claude.json`
   - `~/.codex/auth.json`
   - `history.jsonl`
   - `memories/`

### 6.3 当前仓库需要修正的路径类型

| 路径类型 | 当前写法 | 目标写法 |
|---|---|---|
| 模板路径 | `agents/templates/STORY-TEMPLATE.md` | `{{SCOPE_PACK_TEMPLATES_SHARED}}/files/root/STORY-TEMPLATE.md.tmpl` |
| 工具路径 | `scripts/file_to_markdown.py` | `{{SCOPE_PACK_SCRIPTS}}/file_to_markdown.py` |
| 项目产物路径 | `.output/doc/HLD.md` | `{{PROJECT_OUTPUT_ROOT}}/HLD.md` 或根目录下约定位置 |
| 内部临时状态 | 项目内 `.output/` | `{{SCOPE_PACK_HOME}}/state/` 或系统临时目录 |
| 平台入口路径 | 分散硬编码到各平台目录 | 统一由安装器按平台渲染 |

## 7. 统一管理策略

### 7.1 哪些内容继续作为 canonical source

以下目录继续作为**唯一维护源**：

- `agents/`
- `skills/`
- `scripts/`
- `templates/`

### 7.2 哪些内容改为 canonical fragments + render

旧方案中直接维护的多平台入口，需要改成“共享正文 + 平台模板”的渲染模式。

本轮建议收敛为：

- `rules/AGENTS.md`
- `rules/CLAUDE.md`
- `templates/codex/config.toml.tmpl`
- `templates/codex/hooks.json.tmpl`
- `templates/codex/default.rules.tmpl`
- `templates/claude/settings.json.tmpl`

建议新增：

```text
docs/_canonical/
  instructions/
    common.md
    workflow.md
    paths.md
    install.md
  codex/
    AGENTS.header.md
    config.toml.tmpl
    hooks.json.tmpl
    default.rules.tmpl
  claude-code/
    CLAUDE.header.md
    settings.json.tmpl
```

### 7.3 为什么不再维护“完全共享的 rules 文件”

原因在于平台差异已经明确：

1. **Codex 的 rules 是 `.rules` 执行策略**
2. **Claude Code 的硬权限是 `settings.json.permissions`**
3. **Claude 的 `.claude/rules/*.md` 更像规则文档 / 记忆片段**

因此应改为：

- **共享业务规则正文只维护一次**
- **Codex 与 Claude Code 分别渲染到自己的目标格式**
- **目标项目只看到渲染结果，不看到共享规则源与模板片段**

### 7.4 Meta 自身修改的治理方式选择

当后续需要持续修改以下 5 个 canonical 目录时：

- `agents/`
- `skills/`
- `rules/`
- `scripts/`
- `templates/`

需要决定把“如何修改 meta 自身”放在哪里。当前有 3 个候选方案：

#### 方案 A：只写进 `AGENTS.md / CLAUDE.md`

做法：

- 在平台主指令文件中直接写明 meta 自身修改流程
- 让 Codex / Claude Code 每次都从主指令里读取这些规则

优点：

- 不新增 skill / agent 产物
- 高层规则始终生效

缺点：

- 容易让 `AGENTS.md` / `CLAUDE.md` 变长，污染常驻上下文
- 不适合承载完整操作流程、同步步骤、检查清单
- 两个平台都要维护一份近似规则，长期容易漂移

#### 方案 B：新增 `meta-improve` skill（推荐）

做法：

- 新增一个专门用于“修改 meta 自身 canonical source”的 skill
- `AGENTS.md / CLAUDE.md` 中只保留最小治理规则，并引导优先使用该 skill

优点：

- 按需加载，避免把完整修改流程常驻注入上下文
- 非常适合承载 checklist、影响面分析、sync 判断、状态文件保护规则
- 比 agent 更轻，跨 Codex / Claude Code 更容易对齐
- 更适合当前“目录结构还在调整期”的状态，后续改 skill 即可，不必频繁改主指令

缺点：

- 仍需要在主指令里给出入口提示，否则模型不一定主动使用
- 需要单独维护 skill 文案与边界

#### 方案 C：新增 `meta-improver` agent

做法：

- 定义一个专门负责 meta 自身演进的 agent / subagent
- 通过专用 prompt、权限边界、工具范围来隔离修改任务

优点：

- 更强的角色隔离
- 适合大型重构、并发分析、复杂上下文隔离
- 后续可扩展为专用 reviewer / planner / migrator

缺点：

- 当前阶段偏重
- Codex 与 Claude Code 的 agent 形态差异更大，维护成本高于 skill
- 对“日常修改这 5 个目录”的问题来说，容易过度设计

#### 推荐结论

当前推荐采用：

1. **在 `AGENTS.md / CLAUDE.md` 中只保留最小治理规则**
2. **后续优先新增 `meta-improve` skill**
3. **暂不把 `meta-improver` agent 作为主方案**

原因：

- 这个问题本质上是“修改流程标准化”，更像 **workflow / checklist** 问题，而不是“新增一个长期角色人格”问题
- skill 更适合目录调整期，成本更低，也更容易跨 Codex / Claude Code 对齐
- 主指令文件只保留稳定原则，避免越写越重

#### 建议写入主指令的最小规则

后续可在 `AGENTS.md / CLAUDE.md` 中只保留类似以下内容：

1. `agents/`、`skills/`、`rules/`、`scripts/`、`templates/` 是 canonical source
2. 不直接修改用户目录中的安装产物，除非明确在做适配层同步
3. 不覆盖 `~/.claude.json`、Codex `auth.json`、history、memories
4. 当任务涉及 meta 自身目录调整或 canonical source 修改时，优先使用 `meta-improve`

#### 当前状态说明

由于你还需要继续调整项目目录结构，**本节当前只作为方案记录，不进入立即整改**。

也就是说：

- 现在先不创建 `meta-improve` skill
- 现在先不创建 `meta-improver` agent
- 先把治理决策写入方案文档，等目录结构稳定后再落地

## 9. 平台适配策略

### 9.1 Codex

**设计目标：**

- 保持 `config.toml + AGENTS.md + hooks.json + .rules + skills` 这条真实发现链
- 不再假设“Codex 用户级入口主要是 YAML 产物”

**建议：**

1. 生成或更新 `~/.codex/AGENTS.md`
2. 生成或 merge `~/.codex/config.toml`
3. 生成 `~/.codex/hooks.json`
4. 生成 `~/.codex/rules/*.rules`
5. 安装用户级 skills 到 `~/.agents/skills/`

**额外约束：**

1. 若用户已有 `~/.codex/config.toml`，不得整文件覆盖
2. 仅更新 SCOPE-Pack 管理的键或受控片段
3. 不碰 `auth.json`、history、memories

### 9.2 Claude Code

**设计目标：**

- 继续使用 `~/.claude/CLAUDE.md`
- 使用 `~/.claude/settings.json` 管理可控设置
- 使用 `~/.claude/skills/`、`~/.claude/agents/` 作为发现入口
- 明确不把 `~/.claude.json` 作为常规渲染目标

**建议：**

1. 生成或更新 `~/.claude/CLAUDE.md`
2. 生成或 merge `~/.claude/settings.json`
3. 安装用户级 skills 到 `~/.claude/skills/`
4. 安装用户级 agents 到 `~/.claude/agents/`
5. 如确有需要，再安装 `~/.claude/output-styles/`

**额外约束：**

1. `~/.claude.json` 不覆盖、不托管
2. Claude 的用户级共享扩展优先走 **skills**，不优先走 legacy `.claude/commands/*.md`
3. MCP 用户级配置如果需要纳入，必须通过显式 opt-in 策略处理，不能默认改写 `~/.claude.json`

### 9.3 为什么本轮不优先建设 Claude commands

基于文档分析：

- `.claude/commands/*.md` 已被官方归为 **legacy custom commands**
- 官方推荐方向是 **skills**
- skill 与 command 同名时，**skill 优先**

因此本轮优先级应为：

1. `CLAUDE.md`
2. `settings.json`
3. `skills/`
4. `agents/`
5. `output-styles/`（可选）
6. `commands/`（暂缓，除非明确有业务需求）

## 13. 推荐落地结论

针对当前项目，推荐的最终路线是：

1. **保留 `agents/`、`skills/`、`scripts/`、`templates/` 作为能力源**

5. **把所有模板与工具引用改造成可渲染的绝对共享路径**
6. **统一用 `uv` 作为 Windows / Linux 双平台的工具入口**
7. **明确保护用户状态文件，不做粗暴覆盖**
8. **将 Copilot CLI 明确放到后续阶段，不混入本轮设计**

如果只做“把文件复制到两个用户目录”，可以短期可用；  
如果要做到**真正长期可维护的 Codex / Claude Code 双端共用**，就必须走：

> **共享 runtime + 双平台定向适配 + 安装校验 + 用户状态保护**
