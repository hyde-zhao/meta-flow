## 2. 背景与目标

本方案要解决的不是“再造一个共享 runtime”，而是：

> 在仓库内维护一套 canonical source，经过平台原生渲染后，同时服务 **Codex** 与 **Claude Code**，并把元工作流运行结果写入**被服务工作区**的 `.meta-workflow/`，而不是继续写入 meta 仓库自身的 `.output/`。

本轮的目标收敛为 4 个工作流：

| 工作流 | 目标 |
|---|---|
| 平台渲染 | 统一从 canonical source 渲染到 Codex / Claude Code 原生目录 |
| 工作流路径 | 将活跃实现面从 `.output/` 迁移到 `.meta-workflow/process|checkpoints|delivery` |
| 源文件治理 | 让 `agents/` / `skills/` / `rules/` 真正成为可安装、可审计、可交接的 canonical source |
| 安装闭环 | 支持 dry-run、冲突提示、审计线、卸载与 manifest 记录 |

## 9. 遗留事务

以下事项仍建议保留为后续跟踪项。

### R-01 deprecated 归档文件仍保留旧路径说明

- **对象**：`agents/meta-dm.md`
- **状态**：non-blocking
- **原因**：该文件已明确为历史归档，当前不参与安装流
- **建议**：后续如要做“历史清理轮次”，可单独收口；本轮不应让归档文件反过来阻塞主方案

### R-02 checkpoint / delivery 的运行期自动化仍不足

- **对象**：`.meta-workflow/checkpoints/` 与 `.meta-workflow/delivery/` 的自动回写
- **状态**：non-blocking
- **原因**：本轮完成的是**安装器 + prompt 合同 + 文档治理**，不是完整的运行时编排器重写
- **影响**：当前 checkpoint / delivery 分层主要由 prompt 合同约束，尚未有独立执行器强制落盘
- **建议**：后续如继续推进元工作流自动化，应把 checkpoint / delivery 镜像写入做成显式步骤

### R-03 `INSTALL-MANIFEST.yaml` 采用 JSON 兼容 YAML

- **对象**：`scripts/install.py`
- **状态**：non-blocking
- **原因**：当前实现为了避免新增依赖，使用 JSON 文本写入 `.yaml`
- **影响**：机器可读性没有问题，但对“人工手改 YAML”场景不够友好
- **建议**：若后续需要与外部 YAML 工具链深度互通，再切到真实 YAML serializer / parser

### R-04 `scripts/package_builder.py` 仅完成最小收口

- **对象**：`scripts/package_builder.py`
- **状态**：non-blocking
- **原因**：本轮只收口路径与 Codex 目标面，不把它升级为主安装器
- **影响**：其完整行为尚未做 end-to-end dry-run 验证
- **建议**：如该脚本仍要长期保留，建议单开一轮对齐 `delivery/` 清单和平台结构

### R-05 部分分析类 skill 仍使用逻辑工件名

- **对象**：如 `WORKFLOW-PLAN.yaml`、`SCENARIOS.yaml` 一类逻辑命名
- **状态**：non-blocking
- **原因**：这些描述当前更多指“工件语义”，不是“仓库物理路径”
- **影响**：对人类理解无阻断，但若后续要求所有 prompt 都显式写物理路径，还需要继续统一
- **建议**：作为下一轮“提示词精确化”工作统一收口
